# Subscription analytics

A passive, metadata-only PostgreSQL sink. It measures the proxy traffic that
moves an account's reported usage percentage: requests and tokens per
percentage point, per account and quota window, and how that ratio changes.
It sends no provider requests and does not change the poll cadence.

## Enable

| Env key | Use |
|---|---|
| `USAGE_ANALYTICS_PG_DSN` | PostgreSQL DSN for the writer role. Empty or unset: the sink is off. |
| `USAGE_ANALYTICS_SPOOL_DIR` | Directory for the outage spool. Required when the DSN is set. |

The lowercase forms (`usage_analytics_pg_dsn`, `usage_analytics_spool_dir`) also
work, as for `PGSTORE_*`. The sink starts only in the normal server mode (not in
TUI-standalone). `usage-statistics-enabled` stays `false`: that flag gates only
the Redis usage queue, not usage plugins.

If the DSN cannot be parsed or the spool directory cannot be created, the
proxy logs one error and runs without the sink. The DSN is never logged.

## Database setup (admin)

The proxy never runs DDL. As admin, in this order:

1. Create the roles `cliproxy_analytics_writer` and `cliproxy_analytics_reader`.
2. `schema.sql`: tables (first-install version 1; re-run is safe on version 1;
   it is not a migration tool).
3. `views.sql`: views (drops and re-creates them).
4. `grants.sql`: writer gets `USAGE` + `INSERT` only; reader gets `SELECT`.
   Run it again after each `views.sql`, because dropping a view drops its grants.

## What is stored

- `attempts`: one row per upstream attempt (each retry is its own row).
  `trace_id` is the full UUIDv7 of the inbound request; `attempt_id` is the
  per-attempt UUID; `event_id` is generated by the collector and is the replay key.
  Identity columns are SHA-256 hashes with a fixed domain prefix: `account_hash`
  (auth ID) and `client_key_hash` (client API key). They are pseudonyms, not
  anonymization: a person who can guess an auth ID (often an e-mail file name)
  can confirm it.
  Not stored: request/response bodies, error messages, raw keys, e-mails, auth
  IDs, base URLs, session IDs, other headers.
- `quota_observations`: one row per reported window percentage.
  `source = 'response_header'`: from these response headers only:
  `anthropic-ratelimit-unified-{5h,7d}-{utilization,reset,status}` and
  `x-codex-{primary,secondary}-{used-percent,window-minutes,reset-at,reset-after-seconds}`.
  `source = 'usage_poll'`: a copy of each result of the existing next-reset
  usage poller (only runs when the next-reset routing strategy is active).
  `used_percent` is normalized to 0..100; `raw_value`, `raw_scale` and
  `raw_decimals` keep the reported form.
- `collector_heartbeats`: `start`, one `beat` per minute, `stop`, with cumulative
  drop/spool/error counters per run.

### Timing

Rate-limit headers arrive at response start; token usage is final at attempt
end. `observed_at` of a header row is the time the proxy stored the headers
(`observed_at_quality = 'header_received'`). If that time is unknown,
`observed_at` is the attempt end, an upper bound (`'attempt_end'`).
`observed_not_before` is the attempt start. Polls use `'poll'`, with
`observed_at` = the time the poll response was read.

### Token semantics

`usage_known = false` means the upstream reported no usage; all token columns
are then NULL, never 0. The normalized bucket columns
(`input_uncached_tokens`, `input_cache_read_tokens`, `input_cache_write_tokens`,
`output_non_reasoning_tokens`, `output_reasoning_tokens`, `unclassified_tokens`)
do not overlap, and `total_tokens` is their sum. Add the buckets OR use
`total_tokens`, never both. Do not add the `raw_*` columns: they overlap by
provider. The 5m/1h cache-write split (`raw_cache_creation_5m/1h_tokens`) is
NULL when the upstream did not report it. `auth_kind` NULL means unknown.
All text values are stored as valid UTF-8 without NUL bytes.

### Failure fields

`failure_class` is the verdict of the existing auth classifiers
(`classifier_version` 1): `credential_quota` (provider refused for the whole
credential, e.g. Claude 5h/7d rejection, Codex `usage_limit_reached`),
`rate_limit_unscoped` (429 or quota code without credential scope),
`billing`, `request_scoped`, `transient_transport`, or NULL.
`error_type` / `error_code` are sanitized identifiers (`[a-z0-9_.-]`, up to 64
characters) from the error body.

`origin` is evidence only: `upstream_response` (upstream headers were seen),
`upstream_no_response` (the attempt reached the transport but no headers were
seen), `unmarked` (no evidence either way; this does NOT prove a proxy-made
failure). Some websocket paths can show `unmarked` or `upstream_no_response`
for real upstream answers.

## Views

| View | Content |
|---|---|
| `quota_intervals` | Consecutive observations of one account + window, with the attempts of that account that ended between them, token sums, and flags. |
| `capacity_spans` | Pooled ratios over continuous same-window runs: `successful_attempts_per_pp` (main served ratio), `attempted_per_pp` (also counts failed retries), `total_tokens_per_pp`, and one `*_per_pp` per token category. |
| `capacity_daily` | The same pooled ratios per day (trend). |
| `capacity_span_model_mix` | Model shares inside a span. No per-model ratio: models share one account denominator. |
| `usage_hourly`, `usage_daily` | Successful attempts and tokens by account, provider, auth kind, model. |
| `error_categories_daily` | Failures by origin, class, status, type, code. |
| `collector_health` | Per run: start, last heartbeat, clean stop, counters. |
| `collector_gaps` | Periods over 3 minutes without a heartbeat. |

### How to read the ratios

- Pairing (`quota_intervals.pairing`): `same_window` only when both reset times
  are known and within 120 s. `reset_passed`, `missing_reset` and
  `different_reset` end a span; their traffic is in no span. Reset times are not
  rounded into a match.
- A span's `delta_percent` is the NET change (sum of interval deltas). Zero and
  negative deltas inside one window stay in the span (headers can arrive out of
  order or with another precision), so 42 -> 43 -> 42 -> 43 counts as +1, not +2.
  Span ratios exist only when the net change is positive.
  `negative_delta_intervals` and `zero_delta_intervals` show how often this
  happened. Per-interval ratios exist only for a positive delta.
- `fable_weekly` observations are stored but never form spans: that limit
  covers only some models, while the traffic sums cover all models.
- In-flight counts check only attempts that end within 2 hours after an edge.
- `report_step_pp` is the smallest step the report can show (Claude utilization
  with 2 decimals = 1 pp). A small delta over few steps is coarse.
- Flags to check before trusting a value: `percent_moved_without_traffic`
  (traffic outside this proxy, or header lag), `inflight_at_start/end` and
  `boundary_inflight_attempts` (requests that overlap an edge),
  `usage_unknown_attempts`, `missing_end_attempts`,
  `no_account_attempts_same_provider`, `collector_gap_overlap`,
  `has_upper_bound_timestamps`, and heartbeat drop counters.
- Traffic is placed by attempt end time; headers describe usage at response
  start. Attribution is approximate, not causal.
- Values are demonstrated traffic per percentage point through this proxy, not
  provider limits or full capacity.

## Delivery, outage and shutdown

- `HandleUsage` runs on the usage manager dispatcher. It never blocks: rows go to
  a bounded queue (8192); when full, rows are dropped and counted
  (`queue_dropped`).
- A writer batches rows (500 rows or every 2 s) into one transaction with
  `INSERT ... ON CONFLICT DO NOTHING`. If the database rejects the batch with a
  data or constraint error (SQLSTATE 22/23), each row is written alone: valid
  rows commit, and each rejected row goes to a `*.jsonl.bad` file and counts in
  `spool_dropped`.
- Each database operation has a 15 s context deadline; the pool has at most 2
  connections. This is the collector's own database client, not an upstream
  inference connection, so the AGENTS.md rule against post-connect upstream
  timeouts does not apply; without a deadline a dead database could stop the sink.
- On a write error the batch is written to a spool segment
  (write, fsync, rename, fsync directory). The spool is capped at 512 MiB; above
  that, rows are dropped and counted (`spool_dropped`). Spooled segments replay
  at start and every 30 s, and are deleted only after the insert commits. A
  replay after a crash is a no-op because of the primary keys. Rejected rows in
  a replayed segment are handled row by row as above. `*.bad` files stay for
  recovery and count toward the 512 MiB cap and `spool_bytes`; delete them by
  hand (the space is freed at the next restart).
- Shutdown: the service stops the usage manager and waits (inside the existing
  30 s shutdown deadline) until queued records reach the plugins. Then the sink
  flushes (20 s limit) and writes a `stop` heartbeat. A run without `stop` in
  `collector_health` did not shut down cleanly; rows still in memory then can be
  lost. Records published after the usage manager stops are dropped by the
  manager and are not counted. Records that reach the sink after `Close`
  starts are counted in `queue_dropped`.
- The container stop timeout must be at least 60 s (30 s service shutdown +
  20 s sink close), for example compose `stop_grace_period: 60s`.

## Known coverage gaps

- Requests refused by the proxy before any attempt (all credentials cooling
  down, no auth available) create no row.
- A Claude stream that returns HTTP 200 and then an in-stream `error` event is
  recorded as a not-failed attempt.
- Usage polls exist only when the next-reset routing strategy is active.
- `*.jsonl.bad` spool segments are never deleted automatically. While they
  fill the cap, new outage rows are dropped and counted.
- If the database host does not answer, each flush or replay can stall the
  writer for up to 15 s; the 8192-row queue absorbs traffic during that time.
- Shutdown now waits for usage plugins (inside the existing 30 s deadline);
  a third-party plugin that blocks can extend shutdown up to that deadline.
- Pairing needs a reset time on both observations. After the first day of
  live traffic, check `SELECT window_key, prev_source, source, pairing, count(*)
  FROM subscription_analytics.quota_intervals GROUP BY 1, 2, 3, 4`.
- Traffic of the same account outside this proxy is invisible; it shows only as
  `percent_moved_without_traffic` or lower ratios.
